# Bug: Hardcoded `operation: "read"` during the planning phase

## Problem

In `lib/agent/loop.ts`, when tool calls are returned by the Groq LLM during the planning phase, they are executed via `registry.execute` with a hardcoded `operation: "read"` instead of using the actual operation defined in the tool's `ToolDefinition`.

## Expected Behavior

The agent loop should look up the tool in the `ToolRegistry` and use the actual `operation` property (either `"read"` or `"write"`) from the tool's definition when formulating the `RegistryToolCall`.

## Actual Behavior

It is hardcoded to `"read"`. This currently doesn't cause security breaches only because `ToolRegistry.execute()` performs a secondary check using the real definition (which throws an error since it mismatches the caller's claimed operation), meaning a hallucinated write tool is safely rejected as a registry error. However, this is a fragile setup.

## Reproduction Steps

1. Trace the agent planning loop in `lib/agent/loop.ts`.
2. Note that the parsed tool calls map to `{ ..., operation: "read" }` unconditionally.

## Context

This is a moderate issue. While not currently exploitable due to a secondary guardrail, relying on mismatched assertions for safety is an anti-pattern.

## Relevant Files

- `lib/agent/loop.ts`

## Constraints

None.

## Implementation Plan

1. Edit `lib/agent/loop.ts`.
2. When parsing Groq's output into tool calls, look up the tool definition in the registry (e.g., `registry.getDefinition(toolId)`).
3. Pass `toolDef.operation` instead of the hardcoded `"read"` string.

## Regression Tests

- Ensure `loop.test.ts` still passes and safely rejects unauthorized write attempts during the planning phase.
