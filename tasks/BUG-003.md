# Bug: Eager Corsair singleton crashes on import

## Problem

In `corsair.ts`, the SDK instance is initialized eagerly at the module level (`export const corsair = getCorsair();`). This is eagerly imported in `lib/integration.ts`. Because it runs at import time, any module that imports an integration service (like `GmailService` or `CalendarService`) will crash the Node process during startup if environment variables or the database are momentarily unreachable.

## Expected Behavior

The Corsair SDK should be instantiated or fetched lazily, ideally only at the moment a tool is actually executed (e.g., inside `executeTool()`), to ensure that process startup does not fail due to transient network or configuration issues.

## Actual Behavior

The app crashes at module load time if the environment is not perfectly configured, affecting virtually all routes and services that transitively depend on the integration boundaries.

## Reproduction Steps

1. Corrupt `.env.local` (e.g., remove a required variable) or disconnect the database.
2. Attempt to start the server or run a script that imports `lib/triage-actions.ts` or `lib/agent/service.ts`.
3. The process crashes immediately with an import-time error before any request is made.

## Context

This is an unresolved bug identified previously. Eager initialization in Next.js backend code is an anti-pattern.

## Relevant Files

- `corsair.ts`
- `lib/integration.ts`

## Constraints

Ensure that the lazy initialization still supports tenant-scoped clients (`corsair.withTenant`) correctly.

## Implementation Plan

1. Remove `export const corsair = getCorsair();` from `corsair.ts` or convert it to a function `export function getCorsairInstance()`.
2. Update `lib/integration.ts` in `CorsairIntegrationService.executeTool()` to call `getCorsairInstance()` locally before execution rather than relying on a top-level import.
