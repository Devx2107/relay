# Bug: `TriageActionService` methods query `agent_runs` without explicit tenant filter

## Problem

In `lib/triage-actions.ts`, the `listProposals()` and `approve()` methods fetch records from the `agent_runs` table without an explicit application-level filter ensuring the run belongs to the authenticated user. They rely entirely on Supabase Row Level Security (RLS) to prevent cross-tenant data leaks.

## Expected Behavior

While RLS is the primary security boundary and is correctly configured, application code should practice defense-in-depth by explicitly filtering queries by the user's ID or conversation IDs owned by the user.

## Actual Behavior

Queries like `supabase.from("agent_runs").select(...)` are executed without `.eq("user_id", ...)` or joining on a verified conversation.

## Reproduction Steps

1. Inspect `TriageActionService.listProposals(conversationId)`.
2. Note that it filters by `conversation_id` but does not verify that the conversation actually belongs to the authenticated user before executing the query.

## Context

This is a low-severity hardening suggestion. It is not currently exploitable because RLS is correctly configured on the backend, but it lacks defense-in-depth.

## Relevant Files

- `lib/triage-actions.ts`

## Constraints

The `agent_runs` table doesn't have a direct `user_id` column; it is linked via `conversation_id`. We must ensure the `conversationId` is verified against the `conversations` table for ownership before querying `agent_runs`.

## Implementation Plan

1. Edit `lib/triage-actions.ts`.
2. In `listProposals()`, call the existing `requireConversation(supabase, user.id, conversationId)` helper before querying `agent_runs`.
3. In `approve()`, the run is fetched first to get the `conversation_id`. Update this flow to verify the conversation ownership immediately after fetching the run. (Note: `approve()` does eventually call `getPendingItem` which provides some secondary verification, but making it explicit is better).
