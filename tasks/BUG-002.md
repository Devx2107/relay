# Bug: `relevantAddresses` is populated with the user's own email

## Problem

In `lib/triage-briefing.ts`, the `relevantAddresses` array passed to `rankTriageInputs` is hardcoded to only contain the authenticated user's own email address.

## Expected Behavior

The `relevantAddresses` array should contain the email addresses of people the user actually cares about (e.g., frequent contacts, VIPs, or an organizational directory) so that the triage engine can boost emails and events from these important individuals.

## Actual Behavior

```javascript
const ranked = await rankTriageInputs(inputs, {
  relevantAddresses: user.email ? [user.email] : [],
  ...
});
```

Because the user rarely sends emails to themselves, the `relevantAddresses.has(sender)` check in the ranking engine will almost always evaluate to false for incoming emails. Conversely, because the user is almost always an attendee on their own calendar events, calendar events will indiscriminately receive the maximum relevance bonus.

## Reproduction Steps

1. Log in and load the triage briefing.
2. Note that emails from important colleagues are not prioritized based on sender relevance, because their email is not the authenticated user's email.

## Context

This renders the "sender relevance" signal (intended to be 15% of the overall weight) completely inert or indiscriminate.

## Relevant Files

- `lib/triage-briefing.ts`

## Constraints

Since a full contacts integration might be out of scope for the 12-hour hackathon, we need a lightweight way to pass meaningful addresses (e.g., extracting recent thread participants, passing an environment variable list of VIPs, or querying a simple database table for contacts).

## Implementation Plan

1. Determine the source of truth for "important contacts" for this hackathon (e.g., mock array, environment variable, or Supabase table).
2. Update `lib/triage-briefing.ts` to fetch and pass these addresses into the `relevantAddresses` array instead of just `[user.email]`.
